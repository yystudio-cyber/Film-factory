# 双 3060 工位的制片工程与故障设计

**设计目标**是收到一批剧本后，逐部制作，在任何一次昂贵生成前知道要拍什么，在交付前能把剧本、实际画面、声音与剪辑决定对在一起。1080p、总帧数和文件可解码性可以硬性验收。人物神态、戏剧效果和动作是否自然属于抽样判断，合格率需要用工作站的真实片段校准。

## 为什么选这两种模型

Qwen3-VL-Plus 接受文本、图像和视频。DeepSeek 官方将 V4.1 Flash 的当前 API 名列为 deepseek-flash，也列有视觉能力。此前某个代理仅支持文本，反映该端点的能力；不能据此判断整代模型。没有针对本剧本、该 API 和两种模型的盲测结果，无法给出谁写分镜更好的实测结论。当前部署分工是可检验的工程选择。[Qwen 产品页](https://www.qwencloud.com/models/qwen3-vl-plus) · [DeepSeek 模型表](https://api-docs.deepseek.com/quick_start/pricing/) · [JSON 模式](https://api-docs.deepseek.com/guides/json_mode/)

| 决策 | 输入 | 输出和约束 |
|---|---|---|
| DeepSeek 文本导演 | 原剧本、时长、要求、素材说明 | 场次、分镜、可见动作、现场声、逐字台词、参照素材和稳定身份参考。程序检查字段、时长、帧数、素材存在。 |
| DeepSeek 场记 | 源文本分段、编号镜头 | 将每段和制作要求分配到镜头，区分画面、对白、旁白、标题、字幕、声音和剪辑。逐字项目必须在原文和计划的指定字段中找到。漏项先回到拆镜；第二版仍不合格就停在 GPU 前。 |
| Qwen 分镜审片 | 五个镜内时点、实物或角色参考图、上一镜出口、剪辑点六帧、全镜冻结/黑场测量 | 以实际图像回答每个视觉验收项，保留可见证据。视觉项标成“留给后期”也会退回。较高构图分无法抵消错人物或缺动作。 |
| 两道总审 | FFmpeg 解码的成片联系表、已采用镜头、ASR 记录、后叠文字和逐项证据 | Qwen 对组接后的实际画面给意见；文本导演检查每条原文和明确修订。任一总审退回都会阻止发布。有限次局部重制后仍失败则保留原因。 |
| 确定性执行 | 已校准图、片号、采样参数、FFmpeg 和 SQLite | 负责提交、精确裁切、音频、事务和编号。模型没有执行命令或更改 GPU 参数的工具。 |

对自己的实际模型使用工作站手册中的 compare-directors。宜选一个定版文字镜头、一个跳时空硬切、一个同人物连续动作，记录分镜合法率、遗漏项、提示词返工、人工采用与耗时。文本对照实验不包含 GPU 推理；真实采用率要在实际出片后统计。

## 一部先导片具体怎么生产

以「隧道呼啸 → 爆闪 → 杭州夜研」为例，分镜需分别写出过渡动作、声音承接、工位位置与人物约束。若白闪开始时还需保持隧道运动，首帧可以指定 C006 的干净尾帧；若导演明确要求闪白后硬切办公室，则使用办公室参考图开新镜。两种剪法都需要看**上镜最后八帧范围内的三个时点、下镜最初八帧范围内的三个时点**。完全不同的地点不应仅因像素变化大而被判失败。仪表盘保留最近一次实际镜头提示词、前镜编号、远程任务号、五张抽帧和退回原因，可与作者预期逐镜核对。

一次提交数部影片时，入口先对整份清单校验；SQLite 单次事务入队，批次 token 使网络重试可复用原来的影片 ID。默认整部自动；若清单显式指定 review，完成该镜后进入人工门禁，worker 可去制作其余排队影片。显存不会因为 20 部片同时排队而变成 20 个并发视频任务。原 Studio 若也在向 ComfyUI 投递，双方仍共享远端队列。监视器显示的是共享队列的总数，工厂只跟踪自己的任务票据。

## 故障模式、检测与处置

| 风险 | 当前检测与动作 | 剩余风险或现场恢复 |
|---|---|---|
| 剧本长、单段多事件、强制镜号或反向叙事 | 先保留原文编号，再按镜头分配可验收义务；长片先分场。送入 GPU 前漏项触发一次重拆。 | 场记也是模型，可能把两个事件误判为同一件。用被否片和明确反例做校准。 |
| 明确文字/台词被改写、定版乱码 | 对模型标出的逐字项检查原文与镜头字段，标题/字幕在后期叠加；同期台词做本地 ASR。 | 分词误差、同音人名、字体缺字、旁白音色要现场检查；字体存在不保证包含每个字形。 |
| 参考素材串用、色彩/服装逐镜漂移、掉轴 | 镜头保留前镜片号、根参考及可选角色/场景锚图；每剪检查前后顺序、方向与动作。 | 角色参考要有准确说明。所选图像按内容散列冻结到项目 references 目录，更换素材库原图会影响新项目。基准图用于审片，除首尾帧外不会自动给现有模型新增条件节点。 |
| 快闪、故意停格与模型冻帧混淆 | FFmpeg 全镜扫描持续黑场与冻结区间，附时间给视觉审片结合作品意图。 | 短于阈值的瑕疵、眨眼间变脸、频闪和口型偏差仍可能漏检。 |
| 不连续的现场声、配乐盖住台词、无声 MP4 | 事件型声音写进逐镜提示词；声轨存在性、峰值、配乐时长和最终音画时长检查；混音保留独立配乐。 | 目前使用固定音乐增益与 5 ms 防点击，未实现对白侧链、语义音效辨识或任意 J/L cut。响度和音乐情绪需要试听。 |
| Qwen/DS 网关模型别名错、接口不认 JSON、429 | 可独立配置地址、模型、密钥与扩展字段；429 在短等待窗口内最多尝试三次；空正文、截断和缺行均不能通过。首次渲染前向视觉端点发送随机双色校验图，可以发现只接收文本或忽略图片的网关。 | 网关长期限流、欠费、停服或鉴权失败会把影片标为待处理。工作站需用本机账号验证。 |
| GPU OOM、外部队列抢占、温度或驱动变化 | 单视频 worker；按 prompt_id 检查 ComfyUI 失败状态；监视器显示共享队列、显存和功耗。 | 工厂无法独占外部服务的 GPU。超时不等于任务被远程取消；不强停他人的任务。 |
| 远端接单后丢回执、重复生成 | 原子写入提交意图，再按 client_id 核对近期历史或正在排队的任务。恢复时优先复用远端 ID 和本地下载缓存。 | 历史被清理且无法证明归属时停止。核对原服务后，可显式修改该镜开启一次新制作。不同服务间没有全局事务。 |
| ACE 中断、结果过期或同一个任务被提交两次 | 记录提交中状态和返回的 task_id；已知 ID 可继续轮询。静音和过短的配乐单独记录失败回执。 | 仅留下提交中标志时用 ACE 后台确认并补录 task_id。对已过期且无文件的票据，需要现场确认后归档旧票据再继续。 |
| 磁盘耗尽、网络下载一半、断电 | 低于基础预留时 worker 暂停领取新任务，每十秒复查。开工、渲染与组接前检查任务盘余量；默认保留 2 GiB，加上总线性 PCM 空间。下载先到 .part，完整才替换。重启后显式继续。 | 该数值是可调下限，不能预测第三方缓存或系统盘耗尽。磁盘损坏需要备份。不要把 SQLite 放到 NAS。 |
| 重复点击、同时入队、双进程写入 | 批次内容摘要和 token 去重、事务写入、按本机目录加锁、候选唯一采用约束。 | 两次独立确认的新批次各有新 token。长期运行应备份整个 runs，并按容量归档原始视频。 |
| 重制已采用镜导致下游沿用旧尾帧 | 修改在安全边界执行，重算目标与其后各镜；旧编号和旧文件可回溯。 | 大改前段会引起大量重算。这是衔接正确性的成本。 |
| 误把“文件成功”当作“剧情合格” | 成片通过媒体、视觉和原文总审后开放下载。失败保留清单、候选、测量和诊断。 | 审片模型之间并不统计独立。商业发布或品牌成片应使用人审阈值校准。 |
| 机密素材、多人访问、授权不足 | 网页默认仅绑定本机回环，密钥通过环境变量传递。明确哪些剧本/画面会发给配置的模型服务。 | 当前面向单用户可信工作站；部署公网、跨团队权限、素材授权和对外发布属于另外的部署条件。 |

## 实机验收与容量预算

1. 用现有成功 API 图录入 T2V、I2V、FLF，验证最终节点返回单一正片并带音轨；记录模型版本、图文件和样片。保留原 Studio 使用的低显存设置。
2. 选已采用 C001、C006、曾被否的杭州夜研及修订候选，整理人审标签。检查评审能否指出具体缺陷，统计漏放与误杀；调阈值必须同时观察这两项指标。
3. 做 12 秒左右的三镜样片，包含有意硬切、需要接续动作的镜头、明确文字和现场声。实测不可用的语音模型、字体和网关问题应在扩批之前解决。
4. 再提交多部 60 秒作业。按工作站提供的基线，若每部 10 个 6 秒镜头，每镜一次 1080p 生成约 12–18 分钟，单部仅视频推理约 120–180 分钟。批量吞吐取决于平均候选次数；1.5 次相当于约 180–270 分钟，另加排队、导演、配乐、审片与编码。这是估算，监视器记录实际耗时。
5. 工程验收记录应列出分辨率、准确帧数、时长、失败恢复、人工首轮采用率、剧情遗漏、跨镜缺陷和每成片分钟 GPU 时间。只有实机有代表性的样片才能建立画质与容量承诺。

## 运行边界与恢复演练

- **停电与重启。** 用无关测试项目在渲染途中关闭主控，再重新打开。队列应显示已取消，已采用片号仍在；点击继续后应追领原任务。若 ComfyUI 的历史也被清空，客户端可能再也得不到原票据的归属证据。这种情况应让任务保持待处理，保留实际输出和远程日志。
- **备份与迁移。** 在停止生产并关闭主控后，备份 runs（包括 SQLite、项目媒体和 references）、workflows 和本机配置；密钥通过工作站既有的凭证管理流程恢复。当前数据库部分路径为绝对路径，恢复到原盘符与目录最稳妥。仅复制数据库会丢失候选媒体；在线复制单个 SQLite 主文件也可能漏掉 WAL 中的事务。
- **长期积累。** 合格片、被退回的失败素材和图参数均占空间。当前实行可追溯优先，没有后台自动删片。核对成片与工程备份、片号引用和保留义务后，再由操作者决定归档范围。
- **服务版本或模型别名漂移。** 保留三个流程各一条已接受样片，升级后重复相同提示词、参考图和种子，观察人物、色彩、音轨、耗时和显存。服务商品名相同也可能对应更新后的模型。本站没有锁死云端权重，不能承诺像素级重放。
- **人审校准。** 用“明显合格、明显退回、存在争议”三组样片分别建立基线。按真实工位、人像、运动镜头、定版统计误放和误杀，避免整体平均值掩盖人像镜头的问题。在基准样本量足够前，不设虚构的自动合格率。
- **失败归因。** 首轮被退回率高先看图是否接错、来源是否正确、分镜是否可在给定秒数内完成。若错误集中于同一工作流或所有镜头都无声，修服务比增加重试次数有效。批量制作允许个别影片失败后后续继续；全局 API 欠费会影响使用同一凭证的其他影片。
